# 配置状态与交互菜单性能测试

## 结论

- 常规配置下，状态查询和菜单重绘没有明显卡顿。
- 新增配置参数显示主要增加了 Codex 多模型目录的读取成本：
  100 个模型时，`status` 的中位耗时增加约 1.2 ms。
- 大规模绑定列表存在明显的既有瓶颈：100 个绑定、每个绑定引用 100 个模型，
  一次刷新约 1.37 秒，累计分配约 578 MiB。上一版同样约 1.36 秒。
- 本次只添加性能基准与测量记录，没有修改业务逻辑。

## 环境与方法

测试日期：2026-10-06。

- Linux amd64，Intel Core i5-12600KF，16 个逻辑 CPU，Go 1.24.2。
- 对照版本：`54a6aa5`；当前版本：`28aa70c`。
- 两版使用相同基准代码、假数据、编译参数；`GOMAXPROCS=1`。
- 所有配置、目录与凭据均为临时 fixture；PATH 隔离，不读取真实 Keychain，
  不调用模型 API。确认计时期间 `status` 未修改任何 fixture 文件。
- Go benchmark：每项 5 次，`-benchtime=250ms -cpu=1 -benchmem`，
  表中取中位数。fixture 生成不计入耗时。
- CLI：编译后的独立进程，包含启动与状态查询，每项预热 3 次后执行 100 次。
  新旧版本及场景固定种子随机交错执行，stdout 丢弃，不含终端绘制。
- 本次为温文件缓存测试，不代表冷磁盘、网络目录或真实 API 延迟；
  性能测量未开启 race detector。

## CLI：启动并查询状态

fixture 同时配置 Pi 和 Codex，各注册相同数量的模型、各一个绑定。
其他工具不被检测到。单位：ms。

| 场景 | 上一版中位数 | 当前中位数 | 当前 P95 |
|---|---:|---:|---:|
| 每工具 1 模型，`status` | 2.134 | 2.148 | 2.971 |
| 每工具 1 模型，`status --json` | 2.152 | 2.194 | 3.045 |
| 每工具 100 模型，`status` | 2.576 | 3.783 | 4.604 |
| 每工具 100 模型，`status --json` | 2.542 | 3.750 | 4.608 |

CLI 各项单次样本的标准差约 0.31–0.47 ms；不要把几百分之一毫秒的差异
解读为确定的回退或优化。

## 读取配置、刷新列表与重绘

配置读取包含实际文件读取与解码。模型 ID 使用合成名称，读取基准选择列表中
最后一个模型。菜单固定为 100 列、30 行。

| 操作 / 数据量 | 上一版 ms/op | 当前 ms/op | 当前 KiB/op | 当前 allocs/op |
|---|---:|---:|---:|---:|
| Pi Describe / 1 模型 | 0.0125 | 0.0127 | 3.9 | 43 |
| Pi Describe / 100 模型 | 0.3216 | 0.3153 | 84.3 | 644 |
| Pi Describe / 1,000 模型 | 3.1413 | 3.1330 | 880.7 | 6,048 |
| Codex Describe / 1 模型 | 0.0060 | 0.0061 | 1.7 | 16 |
| Codex Describe / 100 模型 | 0.0058 | 1.0697 | 238.2 | 438 |
| Codex Describe / 1,000 模型 | 0.0058 | 11.4017 | 2,280.2 | 4,045 |
| 刷新 / 10 绑定 × 10 模型 | 2.5269 | 2.5766 | 923.9 | 11,979 |
| 刷新 / 100 绑定 × 100 模型 | 1,362.9534 | 1,373.3974 | 592,225.9 | 6,536,123 |
| 绑定页重绘 / 10 绑定 × 10 模型 | 0.0895 | 0.0768 | 30.1 | 275 |

注意：

- KiB/op 是一次操作的**累计堆分配量**，不是进程常驻内存或峰值 RSS。
- Pi 之前已完整解码模型列表，本次只是读取其中的窗口和输出字段，耗时基本相同。
- Codex 单模型读取全局窗口；多模型需要读取 `model_catalog_json`。
  上一版没有读取目录，因此多模型 Describe 的相对增幅很大，但不能省略读取后
  再把模型预设当成实际配置显示。
- 新旧绑定页布局不同：当前摘要占据部分列表空间，可见列表行减少。
  重绘耗时下降不能解读为底层渲染算法得到优化。

## 已定位的瓶颈

对当前版 `100 绑定 × 100 模型` 场景采集 CPU profile：

- `profileDetail` 累计占 CPU 样本的 99.25%。
- `encoding/json.Unmarshal` 累计占 94.56%。
- `Catalog.ModelSlugs` 累计占 81.05%。

这些是嵌套调用的累计占比，不能相加。

调用链：

```text
loadProfiles
  → 每个绑定调用 profileDetail
    → ModelSlugs
      → 每个模型调用 ModelSlug / Model
        → 重新读取并解码整份 models.json
```

在这份 fixture 中，仅 `ModelSlugs` 路径每次刷新就读取模型表 10,000 次；
再加上默认模型、绑定表、凭据表等重复读取。瓶颈是重复解码，而非摘要文字的绘制。

优先优化方向：

1. `ModelSlugs` 一次读取模型表，再按 ID 查找，不为每个模型重新读文件。
2. 列表刷新时批量读取绑定、模型、provider、credential，复用本次刷新的数据。
3. 保持刷新后立即读取新配置的语义，不先引入跨刷新、可能过期的全局缓存。

## 复现

运行当前版本的 Go 基准：

```sh
GOMAXPROCS=1 go test -p 1 ./internal/tools ./internal/tui \
  -run '^$' \
  -bench 'Benchmark(Describe|LoadProfiles|BindingView)$' \
  -benchmem -benchtime=250ms -count=5 -cpu=1
```

对比旧版时，将两个 `benchmark_test.go` 原样复制到该版本的临时源码副本，再用
同样参数测试；不要在同一时间并行运行新旧性能测试。

本次原始 benchmark 输出、CLI 的全部样本与测量脚本、CPU/内存 profile 保存在
本机 `/tmp/charon-perf.cTP6tF/`，属于临时测量产物，不纳入仓库。
